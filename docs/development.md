# Development

## Setup

Use Python 3.12 or newer and Node.js 22 or newer. From the repository root:

```bash
cp .env.example .env
make install
make migrate
make doctor
make sample
```

`make install-api` creates `.venv` and installs the API in editable mode with development tools.
`make install-web` installs npm packages. Start `make dev-api` and `make dev-web` separately.

For optional scanned-page OCR, install Tesseract separately and add the Python extra with
`.venv/bin/pip install -e "./apps/api[ocr]"`, then set `GROUNDEDPDF_ENABLE_OCR=true`.

Windows developers can use `.venv\Scripts\python`, `.venv\Scripts\alembic`, and
`.venv\Scripts\uvicorn` instead of the Make targets. All application paths use `pathlib`.

## Database migrations

Run from `apps/api` with the virtual environment active:

```bash
alembic upgrade head
alembic revision --autogenerate -m "describe change"
alembic downgrade -1
```

Inspect every autogenerated migration, especially enum, cascade, index, and SQLite batch behavior.
Never edit a migration already included in a release; add another revision.

## Quality commands

```bash
make test
make lint
make format
make build
```

Docker changes must also pass the real runtime check:

```bash
make docker-verify
make docker-down
```

The verification target validates Compose, builds both images, waits for container health, checks the
web health endpoint and API reverse proxy, and confirms that the API process is not root. Use
`make docker-logs` when startup fails.

Backend tests use temporary SQLite databases/directories, deterministic embeddings, an in-memory
vector store for unit isolation, a real persistent Chroma integration test, and the mock chat provider.
They do not require network access. Frontend tests mock typed HTTP/SSE boundaries. Playwright owns the
complete upload-to-citation and insufficient-evidence flow and starts API/web processes in test mode.

## Code organization

- `app/api`: transport coordination and versioned routes
- `app/core`: configuration, errors, security helpers, middleware, logging
- `app/db` and `app/models`: sessions and relational schema
- `app/services`: PDF, storage, embeddings, vectors, documents, settings
- `app/workers`: background ingestion lifecycle
- `app/rag`: retrieval, grounding prompt, answer persistence
- `app/providers`: independent chat transport implementations
- `apps/web/src/api`: typed HTTP and SSE clients
- `apps/web/src/features`: workflow components
- `apps/web/src/pages`: route-level composition

Dependencies point inward toward services and protocols. Keep PDF, vector, and provider exceptions out
of route implementation details. Do not accept citation metadata from the browser.

## Adding a model provider

1. Implement `ChatProvider.stream(system_prompt, user_prompt)` as an async token iterator.
2. Implement a bounded, non-throwing `health()` check.
3. Translate transport failures to `ProviderUnavailableError` without exposing secrets or response bodies.
4. Add the provider selection to the Pydantic setting and `providers/factory.py`.
5. Add mocked stream, timeout/failure, and health tests.
6. Document variables in `.env.example`, README, and troubleshooting.

Do not move prompt construction or citation handling into a provider. Providers are transports.

## Processing changes

Chunk IDs are stable per document, page, and index. Pages are 1-based at the extraction boundary and
remain 1-based everywhere. If a change alters embeddings, normalization, or chunk geometry, test retry
idempotency and document-scoped deletion. Existing documents need explicit reprocessing.

## Pull requests

Keep changes focused, add behavior-level tests, run all quality commands, update documentation when a
command or architecture boundary changes, and follow [CONTRIBUTING.md](../CONTRIBUTING.md).
